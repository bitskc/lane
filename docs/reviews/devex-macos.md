# DevEx review: native-macos-app packaging, docs, tasks, CI

Reviewer lens: docs, packaging, time-to-hello-world, CI, contribution. Verified
against source, the MacBook (~/src/lane, build-mac, /Applications/Lane.app), and
a live `lsregister -dump`. Peer file `docs/reviews/devex.md` is from round 4
(browser-picker-supremacy), so this round's file is `devex-macos.md`.

## Verdict

**Approve with follow-ups.** The build→test→sign→install loop is real and
exercised (20/20 ctest on the MacBook, every nested Mach-O in
/Applications/Lane.app verifies individually, zero /opt/homebrew references),
but the docs trail is Linux-only, tasks.md marks items whose stated acceptance
needed owner-in-person verification, and the `app.lane.Lane` test fixture is
still LaunchServices-registered and can steal `open -b app.lane.Lane`.

## Considered and fine

- **`xattr -dr com.apple.quarantine` unconditional (bundle.sh:130,134):** verified against design.md:155 ("no-op-if-absent step in case a bundle arrived another way"). Running it on an unquarantined local build is a no-op; it cannot remove anything else (single named attribute, recursive). Not needed for the SSH-built flow but harmless and cheap. The surrounding `xattr -rc` inside sign_bundle (:80) is the actually-load-bearing strip before re-signing. Cleared.
- **Sign-in-place dance (bundle.sh:100-117):** verified by evidence, not just reading. `codesign --verify --strict` on every Mach-O inside /Applications/Lane.app passes individually (embedded, not deep-only), `codesign -dv` shows `flags=0x2(adhoc)`, `TeamIdentifier=not set`, Identifier app.lane.Lane. The comment at :68-73 correctly explains why copy-then-sign is required. Verified fine.
- **macdeployqt usage (bundle.sh:46):** `-qmldir="$SRC_ROOT/src/qml"` correct; resulting bundle has Frameworks + PlugIns + Resources/qml populated; `otool -L` on the exe and QtQuick shows zero /opt/homebrew or /usr/local refs, matching the script's own :120-127 gate.
- **Dylib ID rewrite loop (bundle.sh:51-65):** correct ordering (rewrite before signing, since install_name_tool invalidates signatures); framework-vs-dylib naming handles both shapes.
- **LANE_SIGN_IDENTITY override (bundle.sh:14):** default `-` (ad-hoc), correct env override; the keychain-unlock caveat is documented at :3-4.
- **Info.plist.in semantics:** CFBundleIdentifier/Executable/Name/PackageType/Version all sane; LSUIElement matches D3; LSMinimumSystemVersion 13.0 is safe because the only 14+ API (`accessibilityDisplayShouldReduceMotion`, setDefaultApplication content-type call is 12+) is `@available`-guarded at platform_macos.mm:399; unranked CFBundleURLTypes + ranked CFBundleDocumentTypes matches OpenIn/Finicky prior art and the recorded fix (998eae1, 8f874e1); `${LANE_VERSION_STRING}` resolves on Apple because CMakeLists.txt:82-91 sets it in the non-ECM branch.
- **tasks.md owner-attended remainder:** mostly honest. 0.3, 6.2, 6.6, 7.1, 7.2, 9.3, 9.4, 10.1, 10.2 are correctly [ ]; 9.3 is the right single funnel for owner-in-person items; 9.2's scripted gate genuinely ran (bundle state on the Mac corroborates it). Only 6.3's [x] and the 9.2 fixture-note claim break the convention (P1 above).
- **CHANGELOG/RELEASING.md:** no macOS sections yet, but that is the declared state (tasks 10.1/10.2 unchecked, ship gate 9.4 not reached). Not a finding; flagged as open question only because "docs updated after ship" leaves the main README permanently Linux-only if anyone ships without task 10.1.
- **QL check that the icon render file name assumption holds:** `qlmanage -t` emits `<basename>.png` per render, mv renames into the iconset naming scheme; sizes 16..1024 cover the full iconset contract. Fine.
- **README accuracy on Linux claims:** README is accurate for what it documents (Plasma/Wayland/CachyOS) and never claims "Linux only"; it simply omits macOS entirely — tracked as task 10.1 rather than a defect, but worth the P2-adjacent note above.
- **`codesign --remove-signature` + `xattr -rc` strip loop:** correct order (strip extended attrs and all Mach-O signatures before a single deep re-sign), idempotent for the reinstall path.

## Open questions

- Should a macOS CI job be a ship blocker, or is "tested on the one machine that runs it" acceptable for D1's "your Mac first" scope? If the port later becomes a supported platform, ci.yml needs a `macos-latest` leg plus a bundle.sh dry-run step.
- What should the fixture's LaunchServices hygiene be long-term — `lsregister -u` documented in a fixtures README, a `.nosindex`-style path, or a post-checkout hook? Right now any fresh clone on a Mac silently registers a script-as-browser.
- Is the /Applications move worth amending design.md D11 for, or does tasks.md 9.1's as-run record suffice? The two docs now disagree on where Lane lives.
- Does UpdateChecker need a macOS-aware message ("build from source" vs "open release page") until a cask or signed artifact exists?
