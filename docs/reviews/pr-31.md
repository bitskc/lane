## CRITICAL

### 1. `src/core/launcher.cpp:102-117` — `--command=<prog>` before `run` bypasses the interpreter gate

The new pre-subcommand loop skips every leading `-`-prefixed token:

```cpp
for (; i < args.size(); ++i) {
    const QString &a = args.at(i);
    if (a == QLatin1String("--")) { ++i; break; }
    if (!a.startsWith(QLatin1Char('-'))) { break; }
    if (globalOptWithValue.contains(a) && i + 1 < args.size()) { ++i; }
}
if (i >= args.size() || args.at(i) != QLatin1String("run")) {
    return true;
}
```

`--command=sh` is not in `globalOptWithValue`, so it is skipped as a presumed global flag;
`run` is then accepted; the post-`run` scan (lines 121-135) only inspects tokens *after*
`run` and never sees it.

Real flatpak does not work this way. `extract_command()` (app/flatpak-main.c) takes the
first non-dash token as the subcommand and **keeps every option token in argv** for the
subcommand's own GOption parse. Verified live on flatpak 1.18.2:

```
$ flatpak --command=sh run --help
Usage: flatpak run [OPTION…] APP [ARGUMENT…] - Run an app     ← --command=sh applied to run

$ flatpak --command=sh run
error: APP must be specified                                   ← parsed as a run option
```

So `flatpak --command=sh run org.mozilla.firefox` genuinely executes `sh` inside the
sandbox. Lane's gate returns "not blocked" for exactly this argv. The old code
(`args.first() != "run"`) blocked it — this is a **regression introduced by this PR**.

Reachable through both declared trust boundaries:

- A `.desktop` file under `~/.local/share/applications` with
  `Exec=flatpak --command=sh run app.id %u` — discovered args flow through
  `flatpakPrefixArgs` → `flatpakRunArgsBlocked(expandArgs(...))` at launcher.cpp:305-306.
- A hand-edited `config.json` custom target — the case the code comments explicitly name.

The space-separated form `--command sh run` is incidentally still blocked (`sh` becomes the
first non-option token ≠ `run`), so only the `=` form escapes. The same hiding works for
every other `flatpak run` `--opt=val` token (`--env=`, `--filesystem=`, `--socket=`,
`--device=`).

**Fix:** scan the skipped tokens too — simplest correct form is to check *all* args for
`--command=`/`--command` regardless of position (flatpak applies it wherever it appears).
While in there, delete `globalOptWithValue` (see informational #1): real flatpak never
consumes a separate value token for pre-command options, so the plain `-`-prefix skip is
both simpler and more faithful. Add a negative test:
`args={"--command=sh","run","org.mozilla.firefox","$url"}` must return blocked.

Confidence: 10/10 — verified by live probes and confirmed independently by the security
specialist and the Codex adversarial pass.

## INFORMATIONAL (should-fix)

### 2. `src/core/launcher.cpp:95-112` — `globalOptWithValue` models semantics flatpak does not have

Verified live:

```
$ flatpak --installation run list
error: Missing argument for --installation     ← `run` was taken as the COMMAND, not the value
$ flatpak --installation x list
error: 'x' is not a flatpak command            ← `x` was taken as the command
```

Flatpak's command detection takes the first non-dash token, period — no global option
consumes a separate value token. Lane's consumption of the next token is dead logic: every
case it handles is one where real flatpak already errors. Deleting it is fail-closed (the
"value" token then fails the `run` check anyway) and removes ~10 lines. The comment citing
"flatpak(1) GLOBAL OPTIONS" is wrong — those options are per-command options that flatpak
re-parses, which is exactly why finding #1 is exploitable.

### 3. `tests/test_launcher.cpp:336-341` — test encodes semantics real flatpak lacks

`--installation extra run` is asserted to be a valid launch. Real flatpak treats `extra` as
the command (`'extra' is not a flatpak command`) — the launch would fail at runtime. The
assertion only passes because Lane's (incorrect, see #2) value-consumption makes it look
valid. Also, the second launch's argv is never re-verified: `outPath` is overwritten with
no `QTRY` wait, so arg-forwarding for that case is unverified either way.

### 4. `src/core/discovery.cpp:124-131` — `-S`/`--split-string` value consumed but never re-split

`env -S 'prog arg'` puts the *whole command string* in one token. Lane consumes it as the
option value and drops the entry (real env splits it and runs `prog`). Worse,
`env -S 'prog arg' extra` unwraps to `program=extra` — a wrong-program launch, not just a
dead target. Fail-closed in the security sense (the result still passes the interpreter
gate), but the entry silently disappears or mislaunches. Either drop `-S`/`--split-string`
from `envOptWithValue` (→ dead target, honest) or split the value like env does.

### 5. `src/core/discovery.cpp` — `-a`/`--argv0` missing from `envOptWithValue`; bundled shorts misparse

`env -a name prog` → Lane yields `program=name` (dead target; real env runs `prog` with
argv0=name). `env -iu FOO prog` → `program=FOO` (dead target; real env consumes `FOO` as
`-u`'s value and runs `prog`). Both rare and fail-closed; worth a comment or test pinning
the chosen semantics.

### 6. `tests/test_discovery.cpp:821` — weak positive assertion

`any_of(exec=="firefox")` passes even if 3 of the 4 entries misparse — a misparse like
`MOZ_X11=1` survives the negative filter (doesn't start with `-`, isn't `env`, id isn't
`dead`). Assert per-entry: find each target by desktop id and `QCOMPARE` its exec.

Also `tests/test_discovery.cpp:804`: `.insert(16, exec)` is a magic offset
(`strlen("[Desktop Entry]\n")`); a header edit silently corrupts the fixture.

### Residual notes (non-blocking)

- The `dangerousOpts` comment says these options "widen the sandbox", but the check only
  rejects interpreter-named values: `--filesystem=host`, `--socket=session-bus`,
  `--env=LD_PRELOAD=...` still pass. That is the gate's declared scope (blocked
  interpreters), strictly better than round 1, but the comment slightly overpromises.
- Fail-closed false positives, all rare: `--env=FOO=sh` (env assignment whose value is an

  have allowed or errored on — safe direction.
- `--command` value is basename-checked only (`isBlockedInterpreter`, not the symlink-chain
  walk): `--command=mysh` where mysh→bash passes. Pre-existing limitation, mostly
  theoretical since `--command` resolves inside the sandbox's filesystem.
