## User-requested scrutiny

### 1. Leader pinning — is `matched.first()` always `rankForPicker`'s top pick?

**Yes, among visible rows.**

`applyFilter()` builds `matched` by scanning `m_all` in order and appending
targets that pass the filter (`PickerModel.cpp:122-131`). `m_all` is set only
via `reset(rankForPicker(...))` in `Controller.cpp:766` and `:982`, so its
order is the ranker's order. Filtering preserves that order; `matched.first()`
is therefore the highest-ranked target that still matches the filter.

The leader is appended before bucket iteration (`PickerModel.cpp:151-154`);
remaining rows start at index 1 (`:141-143`). This matches issue #33's
required contract.

**Single-target case:** one row, `sectionCount == 1`, section header
"Suggested", no empty trailing sections — sane (`test_pickermodel.cpp` covers
empty list; multi-row cases cover the pinned leader).

### 2. `SectionRole` "Suggested" for row 0 — QML section headers and `visibleSectionCount()`

**Handled correctly.**

`ListView.section.property: "section"` binds to the model's `section` role
(`Picker.qml:228-229`). Row 0 returns `"Suggested"` from `SectionRole`
(`PickerModel.cpp:40-44`); other rows use `sectionFor(t)`.

`visibleSectionCount()` walks the first `min(maxRows, count)` rows and
deduplicates section strings using role `262`, which equals `SectionRole`
(`Qt::UserRole + 6`, same as `PickerModel.cpp:28-36` enum order). Row 0's
"Suggested" section is counted once; card height math stays consistent
(`Picker.qml:20-35`, `:198-199`).

`m_sectionCount` on the model is updated in parallel (`PickerModel.cpp:151-163`)
and matches the tests (`leaderExcludedFromItsSection`, `actionLeaderStillPinned`).
`Picker.qml` still uses `visibleSectionCount()` rather than the
`sectionCount` property — pre-existing; not a regression from this PR.

### 3. Digit mapping — digit 1 → row 0

**Verified end-to-end.**

- `ShortcutRole`: row `i` gets `QString::number(i + 1)` for `i < 8`
  (`PickerModel.cpp:47-50`) → row 0 → `"1"`.
- `Picker.qml:169-173`: when the filter field is empty, `Key_1` … `Key_9`
  call `controller.pick(row)` with `row = event.key - Qt.Key_1` → `Key_1`
  picks row 0.
- Enter/Return pick `list.currentIndex`, reset to 0 on open and on filter
  change (`Picker.qml:43`, `:149`, `:49-50`).

Digit-1, Enter, and `SuggestedRole` all target the same row again.

### 6. Filter behavior — re-pin `matched.first()`

**Correct UX.**

Typing a filter does not re-rank; it narrows the already-ranked list. The
first surviving match stays row 0 (`filterKeepsLeaderFirst` in
`test_pickermodel.cpp:69-82`). When the global leader does not match the
filter, the top match among survivors becomes row 0 — expected for filter
semantics.

### 7. Should the leader stay in its natural section (e.g. Containers)?

**No — pinning is the right tradeoff for this product.**

Row 0 owns pre-selection, Enter, shortcut 1, and `SuggestedRole`. Burying
the ranked pick under a fixed section header (PR #32) broke destination
correctness on the fastest path (issue #33, P1). Pulling the leader into its
own "Suggested" section avoids duplicating the row under "Containers" /
"Browsers" while keeping fixed section order for everything else — strictly
better than issue #33's alternate fix (put leader's section first), which
would still bury non-leader rows of that section below other sections.

### INFORMATIONAL

**[P3] (confidence: 8/10) `tests/test_pickermodel.cpp` — no end-to-end
`rankForPicker()` → `reset()` contract test**

Unit tests pass hand-built target lists into `PickerModel::reset()`. The

`PickerModel{m}.reset(rankForPicker(...)).targetAt(0).id ==
rankForPicker(...).first().id` for a remembered-browser-plus-containers
fixture would lock the full pipeline. Not blocking — current tests cover the
display logic that actually broke.

**[P3] (confidence: 6/10) `Picker.qml:20-35` vs `PickerModel::sectionCount`
— duplicate section-count logic (pre-existing)**

The model exposes `sectionCount` (now updated for the Suggested section) but
the picker window still recomputes via `visibleSectionCount()` in JS. Harmless
today; optional follow-up is to bind height to `controller.pickerModel.sectionCount`
when the visible row cap is not clipping sections.
