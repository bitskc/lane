## Real finding: tracking-param stripping section overclaims the gap

**`docs/designs/competitive-analysis.md` matrix row "Tracking-param
stripping" and the "What competitors have that Lane lacks" section.**
The doc marks this "No" for Lane and calls it "Genuinely missing from
Lane" — the stated justification for recommendation #2.

That's not quite right. `src/core/types.h:107-111` already defines a
`Substitution` struct (`find`/`replace`/`regex`), `Config::substitutions`
is a real field, it's documented in `AGENTS.md:185-195` and
`docs/config.schema.json`, and `pipeline.cpp:41-53` already applies it —
as a find/replace pass over the URL, regex-capable — **before rule
matching**, which is exactly where the doc proposes slotting the new
tracking-param strip. This is functionally the same mechanism the same
matrix row credits Finicky with ("Manual, via user's own `rewrite`
script"), just with no built-in curated list and no settings UI (it's
config.json/CLI only — not exposed in `src/qml`).

So a user or agent can already strip `utm_*`/`fbclid`/etc from a URL
today with a hand-written regex substitution rule. The gap isn't "Lane
has no URL-transform capability," it's "Lane has no curated default list
+ toggle for the common trackers." Recommendation #2's effort estimate
and ranking still hold (a curated list is still cheap to add, still
slots into the same pipeline), but the matrix cell should read something
like "Manual (find/replace substitutions), no curated list" instead of a
flat "No," and "genuinely missing" should be softened to "no built-in
curated list." This was reachable within the doc's own stated grounding
scope (`src/core/{router,matcher,types}.*`) since `types.h` is exactly
where `Substitution` lives.

This doesn't change the ranking of the 3 recommendations or block
merging a docs file, but it's worth a follow-up correction since it's the
one place the analysis is measurably wrong about what Lane already does.

## Recommendation feasibility — checked against the actual architecture

1. **Activity-aware routing scope.** Feasible as described. `MatchScope`
   (`Any`/`Domain`/`Path` in `types.h:29-33`) is a plain enum switched on
   in exactly one place (`matcher.cpp:haystack()`), and `Rule`/scope
   dispatch is uniform enough that an `Activity` variant is a real,
   contained extension, not a rewrite. KActivities isn't currently
   referenced anywhere in this repo (confirmed by grep) — the doc
   correctly frames it as something to add, not something already wired
   in.
2. **Tracking-param stripping.** Feasible, but see the finding above —
   the underlying mechanism (regex substitutions pre-matching) already
   exists; the actual remaining work is a curated list + toggle, smaller
   in scope than "genuinely missing" implies.
3. **Default-browser reclaim watchdog.** Feasible and accurately grounded
   — `refreshDefaultBrowserState()`'s caching and the existing
   `KNotification` call sites (confirmed in `CHANGELOG.md` 0.2.0's
   "Notifications never appeared" fix and the update-checker's
   honest-failure-reason pattern) are real, existing plumbing this would
   reuse.
