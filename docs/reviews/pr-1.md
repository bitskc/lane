# Review: PR #1 — Rename Tern to Lane and fix issues from the review round

Reviewed at commit `c578cac` (branch `lane-rename-and-review-fixes` into `main`). Full diff read (8546 lines), critical paths read in the real checkout, and the two interpreter-blocklist bypasses below were proven empirically by compiling `src/core/launcher.cpp`/`urlutil.cpp` standalone against the unmodified repo files and running them (see Verified reproduction). `ctest --test-dir build` run locally: 10/10 pass.

## Verdict

**REQUEST CHANGES.** The rename itself is clean and complete everywhere it matters at runtime (desktop file, D-Bus service and bus name, systemd unit, AppStream id, notifyrc file and event names, `KNotification::setComponentName`, QML module URI, executable and library target names, tray icon name, autostart id — all consistently `app.lane.Lane` / `lane` / `app.lane`, verified by grep across the whole tree with no stray `tern` left in anything that resolves at runtime). The config migration is genuinely safe: copy-not-move, idempotent, ordered correctly before any config read, and its own corrupt-config quarantine path cannot destroy data even under a same-second race (verified: `QFile::rename` refuses to overwrite an existing destination). But the PR's headline security fix — closing the interpreter-blocklist gap in `targetFromJson`/`launchTarget` — does not close it. Two independent, working bypasses exist (a symlink whose own basename isn't blocked, and `/usr/bin/env <interpreter> ...`), both proven against the actual PR code, not a hypothetical. Since this is presented as "read these closely" security hardening and is not, it should not land as-is. Everything else (activation token handling, unshorten loop guard, router first-match fix, atomic config write) held up under adversarial reading.

**Blocking: 2. Should-fix: 3.**

## Blocking

- **`src/core/launcher.cpp:146,150` and `src/core/config.cpp:127`** — the interpreter blocklist is bypassed by an absolute-path symlink. `isBlockedInterpreter()` only inspects the final path component (`QFileInfo::fileName()`), and both call sites skip canonicalization for absolute paths: `launchTarget()` uses `target.exec` verbatim when it's absolute (line 146), and `targetFromJson()` checks `t.exec` straight from JSON with no resolution at all. A `customTargets` entry with `"exec": "/home/user/.local/bin/totally-a-browser"` where that path is a symlink to `/bin/bash` loads without a warning and launches bash with attacker-controlled args. Proven by compiling `launcher.cpp`+`urlutil.cpp` unmodified and calling `launchTarget()` directly: `isBlockedInterpreter(symlinkPath)` returns `false`, `isBlockedInterpreter(canonicalPath)` returns `true`, and the launch actually ran bash (a marker file was created by the spawned shell). Fix: canonicalize (`QFileInfo::canonicalFilePath()`) before the blocklist check in both places, the same way `resolveExecutable()` already does for the non-absolute path.
- **`src/core/launcher.cpp:15-41,70-72`** — the blocklist never inspects `target.args`, only `target.exec`'s basename, and `env` is not itself on the list. A target with `exec: "/usr/bin/env"`, `args: ["bash", "-c", "<anything>"]` passes `isBlockedInterpreter()` (basename `env` isn't blocked) and launches bash via `env`'s own re-exec, fully defeating the check. Proven the same way: `isBlockedInterpreter("/usr/bin/env")` is `false`, `launchTarget()` returns `true`, and the spawned process ran the injected `bash -c` payload. `xargs`, `find -exec`, `flatpak-spawn`, `nice`, `setsid`, `watch`, etc. all work the same way. A basename-only exec check cannot be complete; either canonicalize *and* reject anything whose first non-flag argument re-invokes an interpreter, or accept that the blocklist is advisory-only and say so in the PR description rather than "now targetFromJson rejects it at load time."

## Should fix before merge

- **`src/app/Controller.cpp:582-585`** — `Controller::persist()` (the single choke point every settings/rule/target-order/remembered-destination change goes through) discards `saveConfig()`'s return value. The whole point of switching to `QSaveFile` was to make a failed write detectable instead of silently corrupting the file; as wired, a failed `commit()` (disk full, permission error, `~/.config/lane` on a read-only bind mount, etc.) is now a *silent no-op* — the user believes the setting/rule/rename they just made was saved, and on next restart it's gone, with nothing in the UI ever having said so. Surface the failure (toast/notification, or at minimum a settings-page banner) instead of dropping the bool.
- **No test exists for `migrateLegacyConfig()`** (`src/core/config.cpp:146-174`, `tests/test_config.cpp`) — confirmed by grep, zero references to `migrateLegacyConfig` anywhere under `tests/`. The function's logic reads correctly on manual inspection (copy not move, skip if destination already exists, skip if source absent, `mkpath` failure handled), but this is exactly the kind of one-shot, run-on-every-startup, can-never-run-again-cleanly code that should have a regression test locking in "never overwrites an existing new-path file" and "leaves the old file intact," given it runs unconditionally on every launch on the author's own machine.
- **`src/qml/Picker.qml:186-187,22-24`** — the picker's visible height is computed as `Math.min(root.maxRows, count) * rowHeight + (count > 0 ? 2 : 0) * sectionHeaderHeight`, hardcoding "2 section headers" regardless of how many distinct `Kind` sections (`Containers`, `Web apps`, `Actions`, `Apps`, `Browsers` — up to 5, see `PickerModel.cpp` `sectionFor()`) are actually present in `m_shown`. Someone with containers *and* custom apps *and* regular browsers (a very plausible setup, arguably the author's own) gets 3+ section headers, which eat more vertical space than the formula budgeted, so rows that should be within the first `maxRows` (and therefore addressable by number-key shortcuts 1-8 per `PickerModel::ShortcutRole`) can be pushed below the scrollable fold. The number key still "picks" that row via `Controller::pick(row)` (which is bounds-safe, so no crash) — it just may silently launch something the user can't currently see, which is exactly the failure mode item 7 in the review brief warned about. Compute the real header count from the number of distinct sections in the current filtered/bucketed list instead of hardcoding 2.

## Follow-ups, safe to merge without

- **`src/qml/pages/TargetsPage.qml:65-75`** (and the equivalent container/pwa/custom drag handlers) — drag-reorder operates on the full per-kind `ListModel` index while the search filter only sets `height: 0`/`visible: false` on non-matching delegates; the underlying rows keep their slot. Dragging a row while a search filter is active can persist an order where a filtered-out row's old position still counts, so the saved order can differ from what was visually dragged. No data loss (nothing is deleted, targets aren't lost), and it self-corrects the moment the user clears the search box and looks again, but it's worth a follow-up to pass only the currently-visible index set into `moveIdAmongSiblings`, or to disable dragging while a filter is active.
- **`src/core/launcher.cpp:162-175`** — the `XDG_ACTIVATION_TOKEN` dance around `QProcess::startDetached` mutates process-wide environment state (`qputenv`/`qunsetenv`) for the duration of one call. This is safe today because the whole app is single-threaded on the Qt GUI event loop and nothing yields between the `qputenv` and the restore, but `getenv`/`putenv` are not guaranteed thread-safe against each other in glibc if any Qt-internal worker thread (DNS resolution, `KNotification`'s D-Bus I/O, etc.) calls `getenv` concurrently. Low probability, but worth a one-line comment or a note if the app ever grows a background thread that touches environment variables.
- **`CLAUDE.md:22`** — "No live reload; restart daemon after edits" is now stale next to `AGENTS.md`'s correctly-updated instructions (`lane --rediscover` reloads config without a restart). Not user-facing, but will mislead a future agent working in this repo into unnecessary daemon restarts.
- **PR body's stated known follow-ups** (`packaging/PKGBUILD` `sha256sums=('SKIP')`, `repoinfo.h` pointing at not-yet-renamed `bitskc/lane`, stale screenshots) are honestly disclosed, correctly scoped as depending on the separate GitHub repo rename, and not this PR's responsibility to fix.

## Verified correct

- **Rename completeness across every runtime-resolved identifier.** Grepped the entire `src/`, `data/`, top-level `CMakeLists.txt`, and `packaging/` trees for stray `tern`/`Tern`/`TERN`: the only two hits are the two intentional, correct comments in `config.cpp`/`config.h` describing the legacy `~/.config/tern` migration source. Desktop entry `Icon=`/`Exec=`/`TryExec=`, AppStream `<id>`/`<launchable>`, D-Bus service `Name=`/`Exec=`, systemd `BusName=`/`ExecStart=`, notifyrc `AppName=`/`IconName=`, `KNotification::setComponentName("app.lane.Lane")` at all three call sites, `KStatusNotifierItem` id and icon, `QGuiApplication::setDesktopFileName`, `KAboutData::setDesktopFileName`, the QML module URI (`qt_add_qml_module(lane URI app.lane ...)`) and every `loadFromModule(QStringLiteral("app.lane"), ...)` call, and the executable/library CMake target names (`lane`, `lane-core`) all agree with each other. This is the exact class of bug ("wrong in a way that fails silently at runtime, not at build time") the review brief called out as historically likely, and it isn't present here.
- **`migrateLegacyConfig()` call ordering** (`src/app/main.cpp:60` vs. every `loadConfig()` call site at lines 34, 115, and inside `Controller::reload()`). It runs unconditionally as the very first statement after `QApplication` construction, before any of the three code paths (`--list`, `--explain`, or normal `Controller` construction) can call `loadConfig()`. There is no ordering window where a fresh Lane process could read the new config path before migration has had a chance to populate it.
- **Migration cannot lose data.** Copies (never moves/renames) the legacy file, only when the new path has no file yet, and does nothing if the legacy path is absent. Running an old Tern binary again after migrating just means its writes go to the old (`~/.config/tern`) path and are invisible to Lane until a fresh migration — a real limitation, but the PR body says so explicitly and it is not a data-loss bug.
- **Corrupt-config quarantine cannot destroy data even on a same-second collision.** Verified empirically: `QFile::rename()` in Qt refuses to overwrite an existing destination and returns `false`, leaving the source file untouched. Two processes racing to quarantine the same corrupt `config.json` within the same UTC second: whichever renames first wins and keeps the corrupt bytes intact at the timestamped path; the loser's rename attempt fails harmlessly and it falls back to defaults with a warning. No file is ever silently overwritten.
- **`QSaveFile` write path itself is correct**: writes to a temp file, checks the byte count written, calls `cancelWriting()` on a short write, and only `commit()`s (atomic rename) on full success. The remaining problem is purely that the caller ignores the result (see Should-fix).
- **Unshorten redirect loop** (`src/core/pipeline.cpp:21-39`). Bounded unconditionally by the `for` loop's `kMaxUnshortenHops = 4`, independent of whether the visited-set cycle detection is even correct — it cannot spin. `isSafeOpenUrl`/`isPrivateOrLocalHost` are re-checked against the *expanded* URL on every hop, not just the first, so a shortener that redirects hop 1 → safe, hop 2 → private/local address is still caught.
- **Wayland activation token handling** (`src/core/launcher.cpp:134-177`, `src/app/Controller.cpp` `openUrl`/`requestActivationAndLaunch`/`startHold`/`confirmHold`). No early return exists between the `qputenv` and the restore in `launchTarget()`, so the token is always cleaned up. `m_pendingActivationToken` is freshly recaptured (or cleared) on every `openUrl()` call, so a later click can never observe a stale token from an earlier one. An in-flight hold is stopped via `QAbstractAnimation::stop()` before a new click is processed, which (per Qt semantics) does not emit `finished`, so the pending hold's launch is never fired with the wrong/next click's token. All of this runs on the single Qt GUI thread, so there's no real concurrency to race.
- **Router first-match / conflict-under-`Never`-policy fix** (`src/core/router.cpp:146-174`). Reread against the pre-fix code (which simply fell out of the conflict branch when `pickerPolicy == Never`, dropping into the remembered/PWA/default fallback and silently ignoring the user's explicit rules): the fix is correct and its test (`conflictHonorsFirstRuleWhenPickerNever`) actually exercises the changed branch.
- **`isSafeOpenUrl`/`sanitizedOpenUrl` gate every URL that reaches `expandArgs`**, so a URL cannot begin with `-` (it's always `http://`/`https://`-prefixed by the time it's substituted into an argv token), which forecloses the classic "leading-dash flag injection" argv attack on the target process even though `expandArgs` does raw string substitution rather than shell-style quoting.
- **`UpdateChecker`'s manual redirect handling** (`src/app/UpdateChecker.cpp:52-101`) is real, reachable code, not a decorative safety net: every redirect hop is independently checked for `https` scheme and non-private/local host before being followed, capped at 3 hops, and a redirect to an unsafe target fails closed with `describeUnsafeRedirect` rather than being silently followed or silently ignored.
- **Container color fallback** (`discovery.cpp` `containerColor()` → `PickerModel::ColorRole` → `Picker.qml`'s dot color): an unmapped/invalid container color never reaches QML as a raw string; `ColorRole` only emits `t.color.name()` when `QColor::isValid()`, and the QML side falls back to a themed neutral rgba. No black dot, no QML color-parse warning.
- **`Controller::pick(int)` / `PickerModel::targetAt(int)` bounds checking.** The picker's number-key handler in `Picker.qml` intentionally allows keys up to 9 through before checking `row < maxRows`, and `PickerModel::ShortcutRole` only labels rows `< 8`; an out-of-range or unlabeled index reaching `Controller::pick()` returns an empty `Target` from `targetAt()` and is a no-op, not a crash.
- **`Controller::addCustomTarget`'s new `QString` return value is actually consumed**: `TargetsPage.qml:650-653` reads it and surfaces it as `customCommandError`, so the parse-rejection messages added in this PR (distinct text per failure reason) reach the user, not just the log.

## Test quality

**Would genuinely fail against the pre-fix code (real regression guards):**
- `test_router.cpp` `conflictHonorsFirstRuleWhenPickerNever`, `pickerExcludesCopyAction`, `pickerExcludesCopyActionEvenWhenPinnedInTargetOrder`, `danglingRememberedKeysFindsMissingTargetsOnly`.
- `test_config.cpp` `corruptConfigMovedAsideNotDiscarded` (checks the corrupt file is moved aside with its exact bytes preserved, not discarded), `customTargetsDropBlockedInterpreter` (against a literal `"python3"` exec — see caveat below).
- `test_launcher.cpp` `launchTargetRejectsBlockedInterpreterEvenWithoutParsing` (literal `/bin/sh` — see caveat below), `launchTargetSetsActivationTokenForDetachedSpawn` and `launchTargetLeavesEnvironmentUntouchedWithoutToken` (both spawn a real child and read back its actual environment — not a mock), `expandsUrlEncodedPlaceholder`, `urlEncodedPlaceholderEscapesUnicode`, `urlEncodedPlaceholderNeverInjectsNewline`, `rejectedCustomCommandErrorsAreDistinctAndActionable`.
- `test_pipeline.cpp` `unshortenFollowsChainedRedirects` (the only one of the three new unshorten tests that actually exercises multi-hop behavior; against pre-fix single-hop code it stops at `tinyurl.com/abc123` and fails the `QCOMPARE`).
- `test_version.cpp` — every test here is a genuine behavioral check on a pure function (`compareVersions`) or on message content (`describe*`), asserting observable differences rather than implementation, and all would fail against a naive or reverted implementation.

**Would pass either way (do not actually prove what they claim to):**
- `test_launcher.cpp` `launchTargetRejectsBlockedInterpreterEvenWithoutParsing` and `test_config.cpp` `customTargetsDropBlockedInterpreter` only test a *literal* blocked interpreter name (`/bin/sh`, `python3`). They pass on the current code and would also incorrectly appear to "prove" the fix is complete, while the two blocking bypasses above (symlink, `env`) sail straight through the same code paths these tests exercise. Add a case with a symlink pointing at a blocked interpreter and a case with `env <interpreter> ...` args.
- `test_pipeline.cpp` `unshortenStopsOnRedirectLoop` — its assertion (`matchUrl` equals either `bit.ly/loop` or `tinyurl.com/loop`) is satisfied by the *pre-fix*, non-looping, single-hop code too: one hop from `bit.ly/loop` lands on `tinyurl.com/loop` and stops there regardless of any loop guard. It does not distinguish "stopped because of the visited-set guard" from "stopped because the old code only ever did one hop." A real regression test needs the mock to return to a URL already seen on hop 3 or later, and assert the visited-set actually terminated it there (e.g. by counting calls).
- `test_pipeline.cpp` `unshortenCapsHopCount` — asserts `calls <= 5`. Pre-fix code makes exactly 1 call and trivially satisfies `1 <= 5`; the test does not prove a cap exists at all, let alone that it's 4. Should assert `calls == 4` (or `QCOMPARE` against the known cap) to actually pin the behavior.
