## Claim-by-claim verification

### 1. Click snapshot through async launch — correct
- `launch()` (Controller.cpp:758) takes `const Click &click` and uses
  `click.openUrl`/`click.host` for the safety check, `launchTarget`,
  failure notification, and toast. No `m_click` reads remain inside it.
- `requestActivationAndLaunch` (Controller.cpp:783) captures `click` by
  value into the `finish` lambda (line 798); both the `.then` callback
  and the 300 ms fallback timer route through it, so the snapshot
  survives the async gap.
- All four call sites pass the right snapshot: `pickId` passes `m_click`
  (449 — picker rows belong to the current click), `applyDecision`
  passes `m_click` (737 — synchronous, same click), hold-finished and
  `confirmHold` pass `m_holdClick` (949, 966).
- `launch()`'s empty-target fallback now ranks the picker from the
  snapshot (`rankForPicker(click, ...)`, 761) instead of `m_click` —
  consistent.
- `copyCurrent` (458) still reads `m_click`. Correct: it is only
  reached synchronously from `pickId`/`applyDecision` while `m_click`
  is the click the picker rows were built from.
- `toast`/`notifyBlocked` carry the snapshot's host (773, 779).

### 2. `m_holdClick` lifecycle — sound
- Set in `startHold` (927) before the animation starts; consumed only
  by the finished lambda (949) and `confirmHold` (966).
- Stale-fire analysis: `openUrl` stops a running hold animation
  (383-386) and `QAbstractAnimation::stop()` does not emit `finished`,
  so a superseded hold never launches. `confirmHold` guards on
  `state() == Running` (961), so it cannot fire after a newer click
  stopped the animation. `cancelHold` never launches. A stale
  `m_holdClick` value is unreachable — no clearing needed.
- `cancelHold` → `showPicker` ordering: `applyDecision`'s new
  `hidePicker()` (728) only runs on non-Pick decisions; `cancelHold`
  bypasses `applyDecision` and calls `showPicker` explicitly (978).
  No interference.

### 3. Dead config removal — complete
- `recentTargetIds` and `toastMs` are gone from `types.h`, `config.cpp`
  (load, save, and the known-keys allowlist), `config.schema.json`,
  `AGENTS.md`, and the test. Zero remaining references in `src/`,
  `tests/`, `docs/config.schema.json`, `AGENTS.md`, `README.md`.
- Removing the per-launch `persist()` loses nothing else: the old
  `launch()` only persisted to save `recentTargetIds` (verified against
  a842f06). All settings/rule/remembered mutations still persist via
  their own `persist()` calls (18 remaining call sites).
- `test_config.cpp` round-trip test retargeted from `toastMs` to
  `holdMs` — still exercises the same load path.

### 4. argv[0] strip — correct
- Both callers pass argv verbatim: `QCoreApplication::arguments()`
  (main.cpp:153) and `KDBusService::activateRequested`'s args
  (main.cpp:144-145). Unconditional `removeFirst()` (319-321) is right;
  the old `contains("lane")` check could treat a renamed binary's
  argv[0] as a URL. Empty `args` is guarded by `!rest.isEmpty()`.
- The dead `rest.contains("--settings")` check removal is safe:
  `--settings` is handled inside the loop (330) via `openSettings()`.

### 5. Queue cap at 4 — reasonable
- `m_pendingUrls` drops oldest, keeps newest (372-376). Correct
  semantic: the newest click is the one the user most likely still
  means; oldest-first draining preserves order among survivors. Each
  queued entry carries its own captured activation token (373, 411-413).
- No test covers this; consistent with repo convention (no
  test_controller.cpp exists — Controller is untested by design).

### 6. holdMs clamp — mostly unified
- Setter clamps 400-5000 (284), schema has minimum 400 / maximum 5000,
  Preferences spinbox `from: 400 to: 5000` (PreferencesPage.qml:60-61).
- **Gap:** `loadConfig` (config.cpp:260) does `toInt(1600)` with no
  clamp — a hand-edited `holdMs: 200` loads as 200 and produces a 200 ms
  hold, below the documented schema minimum. Harmless (animation still
  works, `qMax(1, ...)` at 953), but it means the "one range everywhere"
  claim does not hold for the file-load path. Informational only.

## Findings

### 1. `loadConfig` does not clamp `holdMs` to the schema range
[P4] (confidence: 9/10) src/core/config.cpp:260 —
`c.holdMs = o[QStringLiteral("holdMs")].toInt(1600);` passes a
hand-edited out-of-range value straight through. `holdMs: 200` yields a
200 ms hold despite the schema's `minimum: 400`. Fix: clamp in
`loadConfig` (`qBound(400, ..., 5000)`) or treat out-of-range as the
default. Not a merge blocker — the value is still functional, just
outside the documented range.
