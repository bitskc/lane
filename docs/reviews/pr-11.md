## Critical: `execPrefix` leaks Flatpak's `@@u` file-forwarding marker into every launched browser's argv

**`src/core/discovery.cpp:62-66`:**

```cpp
bool isExecFieldCode(const QString &token)
{
    static const QRegularExpression fieldCode(QStringLiteral("^%[fFuUdDnNickvm]$"));
    return token == QLatin1String("@@") || fieldCode.match(token).hasMatch();
}
```

This strips a lone literal `@@` and bare `%f`/`%u`/etc field codes. It does **not** strip `@@u` — the *opening* marker Flatpak uses to wrap a `%u` field code for file-forwarding. The function's own doc comment (lines 48-56) claims `"@@u ... @@"` markers are stripped; the code only strips the closing `@@`, not the opening `@@u`.

This isn't a hypothetical edge case. Flatpak's exporter (`flatpak-dir.c:8689-8709`) **automatically** rewrites `%f`/`%u` into `--file-forwarding ... @@[u] %[fu] @@` for **any** app whose original Exec used `%f`/`%u` — no opt-in `finish-arg` required. Every browser this PR targets (Zen, Firefox, LibreWolf, Floorp, Waterfox, Brave, Chrome, Chromium, Edge, Vivaldi, Opera, Thorium) declares `MimeType=x-scheme-handler/http;https` and gets invoked with `%u`, so **every one of them gets this wrapping** in its real exported desktop file. Confirmed empirically — this is the actual, currently-installed `app.zen_browser.zen.desktop` on this machine, pulled straight from flathub:

```
Exec=/usr/bin/flatpak run --branch=stable --arch=x86_64 --command=launch-script.sh --file-forwarding app.zen_browser.zen @@u %u @@
```

Not `flatpak run ... app.zen_browser.zen %u` as both the PR's test fixtures and the prior automated review's dismissal ("Browser desktop entries use plain `%u`, not file forwarding, so this is latent") assumed. Running `execPrefix()`'s exact logic against this real line:

```
program:     /usr/bin/flatpak
prefix.args: [run, --branch=stable, --arch=x86_64, --command=launch-script.sh,
              --file-forwarding, app.zen_browser.zen, @@u]
```

`%u` and the closing `@@` get correctly dropped, but the unpaired opening `@@u` survives and gets prepended in front of Lane's own flags in **every** builder (`geckoProfiles` default/profile/private, `geckoContainers`, `chromiumProfiles` default/incognito/tor, `genericBrowser`). A profile launch becomes:

```
flatpak run --branch=stable --arch=x86_64 --command=launch-script.sh --file-forwarding \
  app.zen_browser.zen @@u --profile /home/user/.var/app/app.zen_browser.zen/.zen/xxxx.default \
  --new-tab https://example.com
```

`flatpak run`'s own argv parser (`flatpak-run.c:2766-2777`) treats `@@`/`@@u` as its own toggle for file-forwarding mode, independent of and upstream from anything the browser sees — this is Flatpak's CLI protocol, not something Lane can route around by accident. `@@u` sets `forwarding = true, forwarding_uri = true` and, because the paired closing `@@` was stripped along with `%u`, **nothing ever turns it back off**. Every subsequent arg is now inside an active (unpaired) forwarding region: `--profile` doesn't match the file/dir-separator check and passes through, but the very next arg — the profile directory itself, an absolute path — does start with `/`, so it gets treated as a candidate for document-portal translation and either mangled into a portal doc path (when a portal is running, the common case) or, if no portal is available, `@@u` just ends up passed through as a bogus literal argument ahead of `--profile`. Either way the browser does not receive the profile directory it was told to open. This is exactly the `flatpak --profile ...` corruption bug this PR's own CHANGELOG entry says it fixes — it resurfaces via a different argv token, at the most common real invocation shape (any browser with file-forwarding, i.e. all of them).

**Fix:** strip any token that *starts with* `@@`, not just tokens equal to it:

```cpp
bool isExecFieldCode(const QString &token)
{
    static const QRegularExpression fieldCode(QStringLiteral("^%[fFuUdDnNickvm]$"));
    return token.startsWith(QLatin1String("@@")) || fieldCode.match(token).hasMatch();
}
```

That drops `@@`, `@@u`, and any future Flatpak marker variant in one pass, restoring the invariant the comment already claims.

**Test gap:** neither `discoversFlatpakZenProfile` nor `discoversFlatpakChromiumProfile` (`tests/test_discovery.cpp`) exercises this — both synthesize `Exec=/usr/bin/flatpak run --branch=stable --arch=x86_64 --command=zen app.zen_browser.zen %u`, omitting `--file-forwarding`/`@@u ... @@` entirely, so they pass regardless of whether this bug exists. A regression test needs an Exec line matching the real generated shape (as quoted above) and must assert the resulting `args` list contains **no** token starting with `@@`.

*(confidence: 9/10 — root cause traced to Flatpak's own source, and the exact leaked-token trace reproduced against a live-installed browser's real exported desktop file, not a synthetic one. The one hedge: I did not execute `flatpak run` itself with the corrupted argv to observe the portal's exact failure mode, since that would open a browser window, out of scope for this review.)*

A native Zen (`firstToken` = the real binary path) and a Flatpak Zen (`firstToken` = `/usr/bin/flatpak`, distinct `dataDir`) always land in different groups, so both get walked. - **`flatpakAppId` token selection is safe against the real generator.** Flatpak always emits `--branch=<val>` and `--arch=<val>` as single `=`-joined tokens (`flatpak-dir.c:8672-8676`), never space-separated — so the "a space-separated `--branch 1.0` dotted value could be misidentified as the app id" concern raised in the existing automated review doesn't apply to anything Flatpak itself actually generates; it would only bite a hand-crafted non-standard Exec line, which is out of scope for what this PR needs to handle.

This part of the launch path is fine independent of the `@@u` bug above.

## Lower-severity, non-blocking

1. **(P2, confidence 6/10) Native browsers with extra native Exec flags now get those flags re-injected.** Before this PR, `firstToken(app.execLine)` discarded every token after the binary path; now `execPrefix()` preserves and prepends all of them (minus field codes) in front of Lane's own `--profile`/`--new-tab`. For the common case — `Exec=<bin> %u` — this is a no-op (confirmed: every existing fixture in the test suite still passes, all use bare `%u`). But a native desktop entry that legitimately carries an extra flag before `%u` (distro-patched Exec lines exist for some browsers) would now have that flag land ahead of Lane's args where it previously vanished. No fixture exercises this shape either way, so it's an untested behavior change, not a proven regression. Worth a one-line CHANGELOG mention that the prefix-preservation applies to all `Exec=` lines, not just Flatpak's — the current entry frames this as Flatpak-only.
2. **(P3, informational)** `execPrefix(app.execLine)` is parsed twice per app: once inside `fingerprint()` (only to read `flatpakId`) and again in whichever profile builder runs. Cheap (string parse over a single short Exec line, once per installed browser at discovery time), not worth restructuring `Fingerprint` to carry it through.
3. **(P3, informational)** Two blank lines were left after `flatpakAppId()` (`discovery.cpp:114-115`) — cosmetic, `clang-format`'s job, not calling it out as a real finding.

## Round 2 (commit `5c47a1f`)

### The fix

`src/core/discovery.cpp:62-68`, `isExecFieldCode`:

```cpp
bool isExecFieldCode(const QString &token)
{
    // Flatpak's file-forwarding wrapper emits an unpaired "@@u" opening
    // marker (not bare "@@") alongside the field code it wraps and a
    // trailing bare "@@" closer, e.g. "--file-forwarding app-id @@u %u @@".
    // Matching only exact "@@" left "@@u" in the stripped output, where it
    // corrupts flatpak run's own argv parsing (flatpak reads "@@u ... @@"
    // as a forwarding span). Any token starting with "@@" is a marker.
    static const QRegularExpression fieldCode(QStringLiteral("^%[fFuUdDnNickvm]$"));
    return token.startsWith(QLatin1String("@@")) || fieldCode.match(token).hasMatch();
}
```

`==` → `startsWith`, exactly the one-line fix round 1 recommended. Strips `@@`, `@@u`, and any future Flatpak marker variant sharing the `@@` prefix. The stray double blank line after `flatpakAppId()` flagged as informational finding #4 is also gone.
