## Should-fix (follow-up, not blocking)

1. **`flatpakRunArgsBlocked` never requires the `run` subcommand** —
   `src/core/launcher.cpp:89-108`. Any flatpak argv containing a dotted
   token passes. `exec=flatpak args=["enter","org.mozilla.firefox","sh",
   "-c","...","$url"]` satisfies `hasAppId` with no `--command` and reaches
   `startDetached` — `flatpak enter` runs an arbitrary command inside a
   running instance. Also `flatpak build`, `flatpak debug`. Fix: require
   the first non-`--` token to be `run` (or reject a subcommand blocklist).
   Found independently by Codex and the red-team specialist.

2. **Symlink-named exec skips the flatpak argv check** —
   `src/core/launcher.cpp:272`. The gate is `QFileInfo(exe).fileName() ==
   "flatpak"` on the *resolved* path, and `resolveExecutable` deliberately
   does not canonicalize (:184-192). A symlink named `mybrowser` →
   `/usr/bin/flatpak` passes `isBlockedInterpreterChain` (neither hop's
   basename is blocked) and skips argv inspection entirely:
   `args=["run","--command=sh","app.id"]` launches a shell. Fix: check the
   canonical/target basename for `flatpak`, or walk the chain for a
   `flatpak` hop the way `isBlockedInterpreterChain` walks for blocked
   names. Found by Codex. (Direction: a symlink *named* flatpak pointing
   at a blocked interpreter is already caught by the chain walk; the gap
   is a symlink *to* flatpak under another name.)

## Informational

3. **`env` flags mis-unwrap to a dead program token** —
   `src/core/discovery.cpp:118-125`. `Exec=env -i firefox`,
   `env -u VAR firefox`, `env -- firefox` take `-i`/`-u`/`--` as the
   program → listed target that fails `resolveExecutable` at launch. Not a
   regression (pre-PR `exec=env` was blocked outright), but the unwrap is
   incomplete. Fix: also skip `-`-prefixed tokens, or drop the entry when
   a non-assignment token starts with `-`. (Also flagged by the prior
   automated review on the PR.)

4. **Unwrapped env assignments are silently dropped** —
   `src/core/discovery.cpp:118-125` + `launcher.cpp:298`. `Exec=env
   MOZ_ENABLE_WAYLAND=1 firefox` launches firefox without the variable —
   the packager's intent is lost while the target looks healthy. This is
   the less-wrong option (the alternative, `exec=env`, is blocklisted),
   and `startDetached` can't take a QProcessEnvironment anyway, but it's
   worth a comment/changelog note that env-wrapped entries lose their
   variables.

5. **Malformed flatpak Exec lines discover but can never launch** —
   `src/core/discovery.cpp:248` vs `launcher.cpp:272`. Discovery drops
   only empty programs; `Exec=flatpak run --command=zen` (no app id)
   enumerates a full profile tree whose every target fails the launch
   guard. Fix: mirror `flatpakRunArgsBlocked` (or a shared validator) at
   discovery time.

6. **splitExecTokens ignores spec escapes** —
   `src/core/discovery.cpp:41-68`. `\"` and `\\` inside quotes are valid
   per the desktop-entry spec; the tokenizer drops the backslash and
   toggles on the escaped quote. Rare in real Exec= lines; low priority.

7. **Stale comment contradicted by this fix** —
   `src/core/discovery.cpp:73-74` still claims a native Exec= prefix "is
   empty or a harmless flag" — the bug this PR fixes. Same comment says
   execPrefix matches "firstToken()'s quoting rules" but the dependency
   is now inverted (firstToken delegates to execPrefix, :135-138).

8. **Minor**: `addProfile` comment placement (discovery.cpp:784 — the
   "Still allow Default" comment sits inside the early-return block but
   explains the `key != "Default"` clause); duplicated `appIdPattern`
   regex literal in discovery.cpp:148 and launcher.cpp:91 (separate TUs —
   cross-reference in comments); `expandArgs` computed twice in
   launchTarget (:273, :298) — hoist so inspected argv == spawned argv.
