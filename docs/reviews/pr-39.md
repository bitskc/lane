## User-requested scrutiny

### 1. When does `~/.var/app/<id>/X` → `~/X` translation run?

**Only for desktop entries whose Exec actually invokes `flatpak`.**

`flatpakPrefixArgs()` returns a non-empty prefix only when the parsed
program basename is `flatpak`:

```209:214:src/core/discovery.cpp
QStringList flatpakPrefixArgs(const ExecPrefix &prefix)
{
    if (QFileInfo(prefix.program).fileName() == QLatin1String("flatpak")) {
        return prefix.args;
    }
    return {};
}
```

`flatpakId` is derived only when that prefix is non-empty (`673`). The
translation lambda is a no-op when `flatpakId.isEmpty()` (`682-685`).

A native install whose profile directory happens to live under
`~/.var/app/…` (manual layout, bind mount, etc.) is **not** translated:
its Exec line does not go through `flatpak run`, so `argPrefix` stays
empty and `launchProfileDir()` returns the host path unchanged.

### 2. Other Gecko flatpaks (Firefox, LibreWolf, Floorp, Waterfox)

**The translation does not assume `.zen`.** It strips the host prefix
`paths.home + "/.var/app/" + flatpakId + "/"` and rewrites to
`paths.home + "/" + remainder` (`682-687`). The persist subdirectory is
whatever `fingerprint()` already chose per brand:

| Browser   | `flatpakRelDir` passed to `gecko()` |
|-----------|--------------------------------------|
| Zen       | `.zen`                               |
| Firefox   | `.mozilla/firefox`                   |
| LibreWolf | `.librewolf`                       |
| Floorp    | `.floorp`                            |
| Waterfox  | `.waterfox`                          |

Example: host profile
`/home/user/.var/app/org.mozilla.firefox/.mozilla/firefox/abc123`
becomes `/home/user/.mozilla/firefox/abc123` in argv — matching the
standard Firefox flatpak `--persist=.mozilla` layout. No hard-coded
`.zen` in the translation path.

### 3. Containers and private windows

**Both receive the translated path.**

- Regular profiles: `launchProfileDir(r.path)` in args (`778-778`); host
  `r.path` kept in `t.profileDir` (`784`).
- Containers: `geckoContainers()` now takes `launchProfileDir` and uses
  it in `t.args` (`589`, `650-653`); still reads
  `containers.json` / `extensions.json` via `profile.profileDir` on the
  host (`595`, `602`).
- Private windows: `launchProfileDir(r.path)` in private args (`793-794`).

Test `discoversFlatpakZenProfile` asserts the Work container's args
contain `--profile` but **not** the host `zenDefault->profileDir`
(`291-294`).

### 4. Target IDs, remembered destinations, targetOrder

**Stable — IDs do not embed the profile path.**

Gecko target ids are `browser:<desktop-id>:<profileDirBasename>` where
basename is `QFileInfo(r.path).fileName()` (`777`), e.g.
`browser:app.zen_browser.zen:abc123.default`. Container ids append
`:container:<userContextId>` (`644`).

`remembered` and `targetOrder` in config store these opaque ids, not
argv or `profileDir` (`config.cpp:267-277`, `Controller.cpp:435`).
This PR changes only discovered `args`; ids and `profileDir` are
unchanged, so existing remembered destinations keep resolving.

`launchTarget()` spawns `expandArgs(target, url)` from stored target
args (`launcher.cpp:343`) — it does not reconstruct `--profile` from
`profileDir`.

### 5. Tests

**Yes — argv spelling is pinned.**

| Test | What it asserts |
|------|-----------------|
| `discoversFlatpakZenProfile` | Default Zen target args use sandbox path (`sandboxProfileDir`); `profileDir` still under `.var/app/…` |
| `stripsFlatpakFileForwardingMarkersFromExecPrefix` | Same sandbox `--profile` spelling with file-forwarding Exec line |
| `discoversFlatpakZenProfile` (container) | Work container args omit host `profileDir` |

All 21 `test_discovery` cases pass locally with

Chromium flatpak (`discoversFlatpakChromiumProfile`) is unchanged and
correctly out of scope: Chromium targets use `--profile-directory=<key>`
(profile name), not a filesystem path (`845-846`).

## Findings

### INFORMATIONAL

**[P3] (confidence: 7/10) `src/core/discovery.cpp:682-687` — absolute
`profiles.ini` Path outside `~/.var/app/<flatpakId>/` would skip
translation**

If a Flatpak Gecko install's `profiles.ini` row uses `IsRelative=0` with
an absolute host path that does **not** start with
`$HOME/.var/app/<flatpakId>/`, `launchProfileDir()` returns the host
spelling unchanged and the remoting mismatch could persist. Normal
Flatpak layouts resolve relative paths under `fp.dataDir` (already under
`.var/app/<id>/…`), so this is a rare hand-edited edge case, not the
beelink bug class this PR fixes.

Recommended fix (optional follow-up): document as known limitation, or
add a Firefox-flatpak fixture test if completeness matters.
