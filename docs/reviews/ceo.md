# CEO Review: Tern

Reviewed 2026-09-11, the same day v0.1.0 was tagged. Repo state at review time: 25 commits, one author (Andy Hayes), 0 GitHub stars, 0 forks, 0 issues, no packaging published anywhere. This is day one. Everything below should be read with that timestamp in mind.

## Verdict

**NARROW THE WEDGE.**

The engineering is good and the taste is real: path-scoped memory, a decision order that puts explicit rules ahead of convenience, a hold HUD instead of a silent open, security defaults (http/https only, no shell for custom handlers) that most side projects skip. But right now Tern is a solution built for an audience of one, shipped with zero outside validation, a licensing story that has never been tested against a real buyer, and one already-visible instance of scope creep (containers) shipped into a feature almost nobody can use yet. The move is not to stop, and it is not to keep building broadly. It is to pick the one user who is already proven to be in pain (see below), ship the one thing that would make them switch, and get five real strangers using it before writing another line of settings UI.

## The desperate user

Today, a KDE user running four browser profiles does one of three things: sets a single default and eats the wrong-identity risk every time (personal link opens in the work Zen window, or vice versa), keeps every profile pinned to the taskbar and manually middle-clicks the right icon for every single link forever, or writes their own `.desktop` file hack that the Junction thread shows breaks on newer distro versions for no obvious reason. None of these scale past "I remember which icon is which" and none of them are automatic.

**The desperate user is Andy himself, and by extension any solo consultant or small IT shop juggling multiple client tenants on one machine.** He runs personal Zen, work Firefox, and thirteen `firefoxpwa` apps for different client GitHub orgs, and every misrouted click is a real risk, not an annoyance: pushing to the wrong org, answering a support ticket from the wrong identity, or leaking a client's session into the wrong profile costs him actual client trust, not just seconds. That is a sharper, more expensive version of the "work Google account vs. personal Google account" person, because the number of identities scales with client count, not with life categories, and a consultancy's whole business model depends on never crossing those wires.

## Distribution and licensing

The honest tradeoff, not a settled answer:

**Option A: keep PolyForm Noncommercial + the email-us commercial track.** This protects against the one scenario Andy explicitly worried about (someone repackaging and reselling it), and it is a legitimate choice for source-available software. The cost: it is locked out of Debian/Fedora/openSUSE's official repos on principle, it will read as "not really open source" to the exact KDE-forum crowd that would otherwise star and package it, and right now there is no self-serve way for a business that wants to pay to actually pay. The resale fear itself deserves scrutiny: Junction has been GPLv3 and free for five years with 614 stars and nobody has bothered to repackage and sell it, because the market for a niche Linux desktop utility is too small to be worth reselling. That does not prove Tern is immune, but it is evidence the threat may be smaller than the license is built to defend against.

**Option B: relicense permissively (MIT or GPL) and give up the commercial track.** This removes the one distribution blocker that is fully within Andy's control today: AUR would take it as-is regardless of license, but Flathub, KDE Store, and any downstream distro packager would move faster and with less friction on a plain OSI license, and "will a KDE user actually find this" is a bigger open question right now than "will a business pay for it." The cost is real: no revenue path, and no protection if a well-funded fork ever did want to compete.

**Option C: stay a free personal tool, no revenue, and that is fine.** Andy built this to solve his own multi-tenant workflow first. If it stays there, that is not a failure, it is a scoped and honest outcome, and it removes the entire question. The risk of the current path is chasing Option A's commercial upside without ever validating there is a buyer, while paying Option A's distribution cost the whole time.

**Recommendation, not a decree:** publish the existing `PKGBUILD` to AUR now (zero license conflict, zero cost, already written) to get real Arch/CachyOS users on it, and hold the PolyForm/commercial decision until one of two things happens: a real stranger emails asking to pay, or the AUR/community reception shows the free tier alone is worth optimizing for stars and packaging over revenue. What I might be missing: Andy runs a consulting business and may already have a warm lead (his own clients, or peers in similar shops) who would pay tomorrow if asked directly, in which case Option A with a real price on the page is the faster path and the AUR question is a distraction.

## Moat

**Hard to copy:** the Plasma-native feel. A resident Qt6/Kirigami daemon with a Wayland layer-shell overlay, exclusive keyboard, Plasma accent color, and a hold HUD that can be canceled mid-flight is real platform engineering, not a wrapper. Getting the decision order right (explicit rule beats remembered destination beats unique PWA scope beats picker policy beats default, with longest-path-match and scope narrowing) is also real: it is exactly the kind of small-but-easy-to-get-wrong logic that `test_router.cpp` and `test_matcher.cpp` exist to pin down, and a competitor who tries to skip that work will ship something that "mostly" routes correctly, which is worse than not routing at all.

**A weekend for a competitor:** browser/profile discovery by reading `profiles.ini` and Chromium's `Local State` is exactly the kind of thing the Junction community already half-solved by hand with `.desktop` file hacks. Container support as currently built is thinner than it looks: it is string-templating an `ext+container:` URI into argv and hoping the user has a third-party extension installed to act on it. Tern does not own or control that bridge, so the "hard part" of containers working end to end belongs to someone else's 1.9K-user extension, not to Tern's code. The picker and hold UI, while polished, are QML and taste: reproducible by any competent KDE developer in a weekend.

## The 10-star version

The one capability that would matter most: **own the container bridge end to end instead of depending on a third party's 1.9K-user extension.** Mozilla's Multi-Account Containers has 409K users who have already proven they want identity separation. Tern's container auto-open, as shipped, can only reach the roughly 0.5% of them who happen to also have "Open URL in Container" installed. If Tern shipped and maintained its own small WebExtension (installed as part of Tern's own setup flow, not a hope that the user found a third-party add-on) that closes that gap, container routing stops being a checkbox nobody can use and becomes the reason a KDE user with a real container habit switches. That is a bigger lever than any picker polish, because it turns an already-validated 409K-person need into an addressable one.

## What to cut

Container support is the clearest example of the drift the brief asked to look for. `openspec/changes/initial-tern/proposal.md` explicitly lists "Firefox Multi-Account Containers" under **Out of scope** for v1. It shipped anyway, in the very first `Unreleased` entry after the 0.1.0 tag, before a single outside user had touched the core product. As built today it depends on a companion extension almost nobody has installed, so the code and its three dedicated tests exist to serve a near-empty audience right now. This is not a call to rip it out (it is tested, it is small, and the design note is honest about its own limits), but it is the item that should not have been next, and it is a pattern to watch for on the next roadmap pass: DESIGN.md's stated non-goals (Lua, PDF/mailto) have held so far, which is the good half of this story, so the discipline is not gone, it just slipped once on the item the proposal itself called out.

## Next three moves

1. **Publish the `PKGBUILD` to AUR.** It already exists in the repo and AUR does not care about license freedom. This is the cheapest possible way to get real Arch/CachyOS users on Tern this week, and right now that number is zero.
2. **Post it where the desperate user already showed up.** Junction's issue #9 is four years of a real, repeatedly-asked-for gap that Tern already solves better than the workaround. A short post on r/kde or the KDE Discourse pointing at that exact gap, with build instructions, will produce the first real signal on demand, packaging requests, and whether anyone besides Andy cares. Every other decision on this list (pricing, licensing, what to build next) is a guess until this happens.
3. **Close the container gap or stop advertising it as done.** Either ship Tern's own bridge extension so the 409K Multi-Account Containers users can actually benefit, or move the container claim out of the README's headline feature list until it can reach more than 0.5% of the people who already want it. Shipping code that only 1.9K people on the entire internet can currently use, and calling it a top-line feature, sets up the next reviewer to ask the same question.
