# Rename Tern to Lane: inventory and plan

Status: planning only. Nothing in this document has been applied. No file
was renamed, no identifier was changed, no installed artifact was touched
to produce this inventory (read-only commands only: `grep`, `read`,
`systemctl status`, `xdg-settings get`, `cat`).

New identity, confirmed against `docs/designs/naming.md` (lane is the only
candidate that came back CLEAN on AUR/Flathub/registry/domain checks):

- Binary: `lane`
- Display name: `Lane`
- Reverse-DNS app id: `app.lane.Lane`
- QML module URI: `app.lane`
- Organization domain: `lane.app`
- C++ namespace: `Lane` (see Decision 4)
- Config dir: `~/.config/lane/`
- Repo: `bitskc/lane` (GitHub side, not yet done)

## 0. Totals

**96 files** under the repo (excluding `build/` and `.git/`) contain the
old identity in some form. `build/` additionally contains roughly 140
CMake/ninja/Qt-generated paths and identifiers derived from the project
name; these are not source and are covered separately in 1.14.

Categories found beyond the ten the task listed:

- **1.4 User-visible QML copy** - window titles, an icon source string, and
  in-app help text carry literal `"Tern"` outside of the module-URI
  mechanism the task called out. Six QML files, ~14 string literals.
- **1.9 The `tern.app` organization-domain string** - a second,
  independent reverse-DNS-shaped string (`tern.app`, used as
  `QApplication::setOrganizationDomain` / `KAboutData::setOrganizationDomain`)
  that is easy to conflate with the `app.tern.Tern` application id but must
  be renamed separately, to `lane.app`. It also leaks into
  `docs/config.schema.json`'s `$id`.
- **1.12 Test fixtures** - a discovery-test desktop file
  (`tests/fixtures/desktop/app.tern.Tern.desktop`) and a one-line comment
  in eight `prefs.js` fixtures (`// tern test fixture profile`).
- **1.13 The `openspec/changes/initial-tern/` directory name** itself.
  Also `docs/designs/tern-office-hours.md`'s filename.
- **1.14 The `build/` directory** cannot be find-and-replaced; it must be
  deleted and regenerated by CMake, or every generated identifier
  (target names, autogen dirs, `.qrc` files, `tern_version.h`,
  `libtern-core.a`, `bin/tern`) will silently keep the old name next to
  new source that no longer matches it.
- **The PolyForm license "Required Notice"** in `LICENSE` embeds the repo
  URL as a legally meaningful string (PolyForm's Required Notice
  mechanism), not just documentation prose - flagged separately in 1.11
  so it isn't casually sed'ed.
- **`Controller::makeDefaultBrowser()` and `isDefaultBrowser()`** shell out
  to `xdg-mime`/`xdg-settings` with the literal string
  `"app.tern.Tern.desktop"` - this is the code path that actually claims
  or checks default-browser status, not just cosmetic text.

## 2. Decisions

### 2.1 Config migration

**What is actually in the file right now** (read, not modified):
`autostart: false`, `closeOnFocusLoss: true`, `holdMs: 3186` (hand-tuned
away from the 1600 default), `defaultTargetId` set to a real Zen profile,
`pickerPolicy: "no-rule"`, `preferPwa: true`, `showUrl: true`, `toast: true`,
`toastMs: 2800`, `unshorten: true`, `unwrapO365: true`, `version: 1`, and
`recentTargetIds` populated with 8 real browser/profile/PWA ids. `rules`,
`remembered`, `targetAliases`, `targetOrder`, `customTargets`, and
`hiddenTargetIds` happen to be empty arrays/objects right now, but the
migration must handle them as data, not assume they'll always be empty.

**Recommendation: copy-on-first-run, destination-wins, never delete the
source.**

Add a small `migrateLegacyConfig()` step (in `src/core/config.cpp`,
exported alongside `defaultConfigPath()`), called once at the very start
of `main()` before argument parsing does anything path-dependent
(`--config-path`, `--list`, `--explain`, daemon start, and GUI settings
all need to see the post-migration state consistently):

1. Compute `newPath = defaultConfigPath()` (`~/.config/lane/config.json`)
   and `legacyPath` (`~/.config/tern/config.json`) explicitly, without
   going through the renamed function twice.
2. **If `newPath` already exists, do nothing and return.** This is what
   makes the whole operation safe to run twice, and safe when both paths
   have content: the new location, once it exists, is authoritative and
   is never overwritten by the migration again.
3. **Else if `legacyPath` exists**, create `~/.config/lane/` if needed
   (`QDir::mkpath`) and `QFile::copy(legacyPath, newPath)`. Copy, not
   move or rename: the original file at `~/.config/tern/config.json` is
   left byte-for-byte intact no matter what happens next. If the copy
   fails (permissions, disk full), log to stderr and fall through -
   `loadConfig()` already knows how to create a fresh default config
   when nothing exists at `newPath`, so a failed migration degrades to
   "start fresh," not a crash.
4. **Else** (neither exists): do nothing; `loadConfig()`'s existing
   default-config path handles first-run same as today.
5. Log the outcome once (`qInfo()`), e.g.
   `"Migrated config from ~/.config/tern to ~/.config/lane"`, so it's
   visible in `--daemon` output or `journalctl --user -u lane` without
   depending on the user noticing.

This satisfies every constraint in the task: it can never lose data
(source is never deleted or overwritten, destination is never
overwritten once it exists), it is idempotent (step 2's existence check
is the only branch that matters on a second run), and "both exist" has
defined behavior (new wins, old is left alone for the user to compare or
delete by hand). The old `~/.config/tern/config.json` becomes an inert
backup after migration; cleaning it up is a manual step, covered next.

### 2.2 The old install

**Recommendation: script the removal of stale files; keep "set as
default" opt-in and manual, matching the app's existing design.**

Rationale: this machine's `mimeapps.list` right now names
`app.tern.Tern.desktop` as the actual default for `http`/`https`/`text/html`,
and a live process is running `~/.local/bin/tern --daemon`. If the old
desktop/D-Bus/systemd/notify/icon/metainfo files are simply left in
`~/.local/share/*` after a new `lane` install lands, Plasma still has a
fully-formed, D-Bus-activatable "Tern" application definition sitting
around. It won't silently override the new default (mimeapps.list is
explicit, not last-writer-wins), but it will still show up in "Open
With" pickers, `plasma-integration`'s app list, and D-Bus activation
(`app.tern.Tern`) forever, which is exactly the confusing half-migrated
state the task is worried about. A six-file removal is small and
mechanical enough to script safely; re-pointing `mimeapps.list` to the
new default is a different kind of action (it changes what opens every
http link on this machine) and should stay a deliberate, one-click
action through the new app's own Settings -> "Use Lane as default
browser" button, the same opt-in path a first-time install already uses.
That keeps the project's stated design principle ("Opt-in default
browser") true through the rename instead of a script grabbing default
status on the user's behalf.

Concrete cleanup, safe to re-run (only acts on files that exist):

1. Stop the running old daemon: `systemctl --user stop tern.service`
   if it were active (it currently is not - the live PID was started
   directly, not via systemd) and kill the actual running
   `~/.local/bin/tern --daemon` process.
2. `systemctl --user disable tern.service` (currently already disabled,
   but idempotent) and remove `~/.local/share/systemd/user/tern.service`.
3. Remove `~/.local/share/applications/app.tern.Tern.desktop`,
   `~/.local/share/dbus-1/services/app.tern.Tern.service`,
   `~/.local/share/knotifications6/app.tern.Tern.notifyrc`,
   `~/.local/share/icons/hicolor/scalable/apps/app.tern.Tern.svg`,
   `~/.local/share/metainfo/app.tern.Tern.metainfo.xml`.
4. Remove `~/.local/bin/tern` only after confirming `~/.local/bin/lane`
   exists and runs (do not remove the only working binary before its
   replacement is verified).
5. Explicitly do **not** touch `~/.config/tern/` here - that is Decision
   1's job, and it should run first so the migration source still exists
   when it executes.
6. Leave `~/.config/mimeapps.list` alone; let the user (or the user
   running the new app once) click the existing "Use Lane as default
   browser" button, exactly like first install.

### 2.3 The v0.1.0 tag and PKGBUILD

**Recommendation: regenerate the checksum right after the GitHub repo
rename, do not wait for the next tag.**

The task's premise is correct: GitHub generates tag source tarballs
on demand from the repository's *current* name, not the name at tag
time, so `bitskc/tern`'s `v0.1.0` tarball and `bitskc/lane`'s `v0.1.0`
tarball (same commit, same tag) will unpack into a differently-named
top-level directory (`tern-0.1.0/` vs `lane-0.1.0/`), which changes the
tarball's bytes and therefore its sha256. The current
`sha256sums=('b881390...')` in `packaging/PKGBUILD` will stop matching
the moment the GitHub repo is renamed, with no code change required to
break it.

Two options exist; recommending the first:

- **(Recommended) Regenerate now.** Update `pkgname=lane`,
  `url="https://github.com/bitskc/lane"`, and the `source=` line to
  `.../bitskc/lane/archive/refs/tags/v$pkgver.tar.gz` as part of the
  rename commit, then, immediately after the GitHub-side rename is
  done (a step outside this repo, done via GitHub's own rename UI/API),
  download that exact URL and run `sha256sum` on it to get the real
  checksum - a mechanical, verifiable action, not a guess. `v0.1.0`
  already shipped as a real tag; there's no reason to leave packaging
  broken for an unknown number of releases just to avoid one curl and
  one `sha256sum` call.
- **(Fallback) Hold the PKGBUILD.** If the GitHub rename cannot happen
  in the same session as the source rename, leave `packaging/PKGBUILD`
  updated for identity fields only (`pkgname`, `url`, `pkgdesc`) and
  mark `source`/`sha256sums` as pending in a comment, to be finished the
  moment the GitHub repo is actually renamed. Never fabricate a
  checksum to fill the gap.

Either way: do not touch `v0.1.0`'s tag content or message. The tag is a
historical marker of what shipped as "Tern"; only the PKGBUILD that
*fetches* it changes.

### 2.4 Namespace `Tern`

**Recommendation: rename it to `Lane`.**

It's the one piece of this rename with zero external contract - nothing
outside this repo links against `Tern::`, there's no installed header,
no library consumers, no ABI to preserve. The only cost is mechanical:
~35 files each touch it in exactly two predictable spots (`namespace
Tern {` / `} // namespace Tern`) plus a handful of `Tern::` qualifications
in `main.cpp`, all uniform enough for a single scripted pass (`ast_edit`
or `sed` on the two patterns) rather than hand-editing. The cost of *not*
renaming it is permanent and compounding: every future contributor
opening any `.cpp`/`.h` in this project sees `namespace Tern` inside an
app called Lane and has to be told "that's the old name, ignore it" -
forever, for a change that's free to make correctly right now, in the
same pass as everything else. Do it in the same commit as the QML
module URI and CMake target renames (1.1/1.3), since a build is required
to verify all three anyway.

## 4. How to verify it worked

Concrete, runnable checks, not "looks right":

- **Build is clean and self-consistent**: `rm -rf build && cmake -S . -B build && cmake --build build` succeeds with zero references to `tern` in the generated `build/` tree (`grep -ril tern build/` returns nothing once the source-level rename is complete and the directory is regenerated).
- **Tests pass**: `ctest --test-dir build --output-on-failure` - all `test_*` binaries (renamed via `lane_test()`) pass, including whatever `test_discovery.cpp` case reads the renamed fixture desktop file.
- **The QML module actually loads** (the silent-failure risk called out in 1.3): run `lane --daemon &`, then trigger a picker (e.g. open an unmapped URL via `lane`'s own CLI or a real link click) and confirm the picker window appears - not just that the process doesn't crash. Check stderr for the absence of `"Lane: picker QML failed to load"`. Repeat for Settings (open from tray) and Hold (trigger a remembered/PWA/default open).
- **D-Bus name registers**: `busctl --user list | grep app.lane.Lane` shows the service once `lane --daemon` is running; `qdbus --session | grep app.lane.Lane` as an alternative check. Confirm `app.tern.Tern` no longer appears after cleanup.
- **Desktop entry activates**: `gio launch ~/.local/share/applications/app.lane.Lane.desktop` (or double-click via a file manager/app launcher) opens Settings; `update-desktop-database ~/.local/share/applications` reports no validation errors.
- **KStatusNotifierItem and notifications**: confirm the tray icon appears with the `app.lane.Lane` icon, and that triggering a launch-failed or opened notification actually shows a toast (this exact failure mode - notifications silently dropped because `setComponentName` didn't match the installed `.notifyrc` - is called out in `CHANGELOG.md` as a real bug this project already hit once with the old name; the rename must not reintroduce it under the new name).
- **Config survives**: before the rename, note the exact contents of `~/.config/tern/config.json` (already captured in Decision 1 above). After first run of the renamed binary, confirm `~/.config/lane/config.json` exists with identical content, and that `~/.config/tern/config.json` still exists, unmodified, byte-for-byte (`diff` or checksum both). Run the renamed binary a second time and confirm nothing changes (idempotency).
- **`--config-path`, `--list`, `--explain` still work**: `lane --config-path` prints the new path; `lane --list` and `lane --explain <url>` run without needing the daemon, matching the documented agent-friendly CLI contract in `AGENTS.md`.
